Cold outbound fails on quality long before it fails on volume. Writing an
opener that reads like a person wrote it means reading something about the
company first, and that research is the part nobody has time for. A model
will do it in a second, and it will just as happily produce filler with the
right shape and nothing inside it. So the interesting engineering question
is not how to generate the email. It is what stands between the model and
the sender.

I built this flow around that check. Apollo's free plan has no prospecting
API, so the list arrives as a saved-search export the flow reads off disk,
and the column mapping lives in config rather than in code, because Apollo
writes a different header set for every export preset. On the published run,
12 of the 13 mapped fields resolved and the flow said which one did not.

## How it works

**The gate is deterministic and it loops instead of sending.** Four rules: the
body has to be 25 to 60 words, it cannot contain a denylisted opener or an
unfilled template token, it has to name the prospect's company, and it cannot
copy a run of more than 15 words out of the research notes. A rejected draft
goes back to the prompt with the rule it broke attached, twice at most, and
then lands in a review queue instead of being sent anyway. The cost is that a
rejected prospect burns three model calls, and a decent draft can still lose
on a technicality. I took that over a run that quietly ships something
generic. On the clean run all 17 drafts passed first time at 35 to 43 words.
On the rejection drill I told the writer to open with a stock line and skip
the company name, and the gate refused all 51 attempts by rule number.

**The draft is written down before the sender is called.** Each approved draft
becomes an outbox row marked pending, and only then does the send happen.
Success flips the row to sent, failure flips it to failed with the error text.
That is two extra writes per prospect and a table to keep. I proved it was
worth having by making the send call fail on all 17 items: every draft was
still sitting there afterwards, with the reason.

**Prospects move five at a time, with a two second pause between batches.**
Whole run: 20 seconds for 17 prospects, 8 of which are that pause. The
throttle is there because the model, the sender and my own patience for
debugging all prefer a slow loop to a burst, and the batch boundary is where
a retry can restart without redoing work.

One more thing this build refuses to do. The prospects are real, so every
send is forced to a single lab address before the sender runs, and that node
throws if the address is still a placeholder. The personalization is real.
The delivery target never was.
