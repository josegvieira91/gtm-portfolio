Target account lists are easy to buy. The firmographics are usually stale,
and enrichment bills per answer, so the order you call vendors in decides
the cost. I built this waterfall on Clay's free plan, 100 data credits a
month and 200 rows per table, and in the run replayed below 40 synthetic
accounts went through three enrichment legs, 16 reached HubSpot, and the
plan's credit counter did not move.

## How it works

**Ordering the providers.** The list arrives from Google Sheets into a Clay
table, deduplicated on domain as it lands. Three legs then run in sequence.
Clay's own company enrichment goes first at one credit a row, LeadMagic
follows, and the company's own internal registry answers last. I kept
vendor-first because the case was meant to exercise the paid legs and their
gates. On a paying account I would put the registry first, because internal
data is free and fresher than anything a vendor sells.

**What counts as a miss, and what a miss opens.** Clay's per-column run
condition would not persist for me, so I built the cascade into the inputs
instead. A formula column emits the domain only when the leg before it came
back empty, and the next leg reads that column as its required key. A leg
with no key does not run, so it cannot bill. In this run that gate never
closed: Clay's leg missed all 40 rows, LeadMagic then missed all 40, and
every row went on to the registry. The skip path is built and visible in
the table, but this run did not exercise it.

**What a repeat costs.** Auto-run stays on with "keep existing results"
checked, so only errored, empty or new cells should fire. I re-ran the
waterfall over ten rows: the confirmation dialog quoted about 20 credits
and the counter moved by zero. On this list that proves misses are free,
not that filled cells are skipped, since every vendor cell was a miss. The
skip setting only gets a real test on a list where a vendor matches. Over
the full 40-row run the workbook spent 0 of its 100 credits, because Clay
charges for a successful enrichment and every domain here is a reserved
example.com address. The table's Sandbox Mode control was not checked for
this run.

**Verdicts, and the write to HubSpot.** I seeded the registry with 20 of
the 40 domains, so the 50% describes the seed. What the run shows is that
each of those 20 was filled by the registry after both vendors missed. The
ICP rule is 25 to 500 employees, Canada or the United States, and one of
seven industries; sixteen rows passed it. Clay's HubSpot connector would
only sign in to a personal account, so an n8n workflow reads the output
sheet and writes to HubSpot, matched on domain, one search at a time
after the first loader run (#112) hit HubSpot's rate limit. In run #115
all sixteen were already in the lab portal, so the create branch did not
run. The other twenty-four kept a verdict: not enriched, or enriched and
outside the rule. I would rather hand sales 16 accounts plus 24 labelled
rejects than 16 accounts with no trace of the rest, because then nobody
can tell a vendor gap from an ICP decision.

The download is the case folder. The Clay file is a transcription of the
table, column by column, because Clay free has no export; the loader file
is a real n8n export.

**What this run does not prove.** Both vendors miss every synthetic domain
by construction, so it says nothing about vendor match rates, about what a
real list would cost (up to one credit per enriched row on each vendor
leg), or about whether a filled cell is skipped on a re-run. A closed gate
never happened. The coverage figure is the seed, and the HubSpot write is
sixteen updates with no create.
