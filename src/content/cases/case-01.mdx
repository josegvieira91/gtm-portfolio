This flow puts a web form submission in front of a rep in Slack, scored,
with an owner and a HubSpot record, and nobody opens an inbox. In the run
replayed below, a synthetic lead reached its owner in 5.3s while
the enrichment service refused every call.

## How it works

**Intake.** The form posts server-side with a header token, so no
browser holds it. The idempotency key is a SHA-256 of
the form's submission_id, or of the normalized payload when there is no
id. A double click or a webhook retry gets the same key and stops before
enrichment runs. An edited resubmit gets a new key and counts
as a new lead. I accepted that: dropping a real lead costs more than an
occasional near-twin.

**Persist first.** The payload goes into Postgres before the gate runs,
duplicates included. If a later step dies, the payload is there to
replay by hand. A submission that fails validation gets a 400
and is not stored.

**Enrichment.** The enrichment service here is a local mock, set to
answer 429 for this run. n8n tried three times, 1.5s apart,
gave up after 3.0s, then the flow fell back to the form's
firmographics and marked enrichment pending. A lead scored on
form data alone is less precise. A lead waiting on a vendor is not being
worked at all.

**Scoring and routing.** Five explicit rules in a config block, so the
same input always gets the same score. An account that already has an
owner keeps it; a new account takes the next rep from a round-robin
pointer in Postgres, so two runs cannot grab the same slot.

**CRM.** The company is looked up by domain and the contact by email,
updated when found and created when not, so a rerun never makes a second
of either. Both writes retry 429s, 5xx answers and network errors with
exponential backoff and honor Retry-After: one call plus up to five
retries. Any other 4xx gives up at once. Either way the reason is written
to the lead row and the alert still goes out. Every
lead that passes the gate ends up as a Postgres row with a status,
qualified or not.

**Alert.** The Slack message is written to an outbox row before it is
posted. A failed post marks the row failed with the error; a retry branch
posts it again every five minutes, up to three attempts.
The alert reaches a shared channel with company, contact, score, domain
and rep. The lab reps have no HubSpot user ids, so the HubSpot owner
field stays empty.

**What this run does not prove.** It is one lead for one new account.
Two leads for the same new account arriving together would both find no
owner, and the second would overwrite the first; that race is not
handled. The 429 came from a mock I configured, not a real vendor. The
duplicate, existing-contact and failed-Slack paths ran in separate lab
executions.
